## 🔴 КРИТИЧЕСКИЕ — могут сломать бота прямо сейчас

### C1. Отчёт >4096 символов падает с ошибкой

**Файл:** `bot.py:601-609`
**Функция:** `analysis_filter_handler`

`analysis_filter_handler` отправляет отчёт через `reply_text`, а не `send_long_message`. При большом количестве заявок отчёт превышает лимит Telegram (4096 символов) и бот получает `BadRequest: Message is too long`.

Все остальные места (`run_analysis`, `scheduled_report`) корректно используют `send_long_message`.

**Исправление:** Заменить `reply_text` на `send_long_message` с `reply_markup=keyboard`.

---

### C2. split_message ломает HTML-ссылки при разбивке

**Файл:** `utils.py:100`
**Функция:** `split_message`

При разбиении длинного отчёта, если точка разреза попадает внутрь `<a href="https://example.com">текст</a>`, код на строке 100 восстанавливает тег как `<a>` **без атрибута `href`**. Telegram отклоняет `<a>` без `href` как невалидный HTML.

Код переоткрытия тегов:
```python
reopen = "".join(f"<{tag}>" for tag in open_tags)  # теряет атрибуты
```

**Риск:** Отчёты с длинными примечаниями, содержащими ссылки, будут обрезаны с потерей кликабельности или полным отказом отправки второй части.

**Исправление:** Сохранять атрибуты тегов в `open_tags` (хранить полное содержимое тега, а не только имя).

---

### C3. get_photo_counts падает при >999 заявках

**Файл:** `db.py:301`
**Функция:** `get_photo_counts`

```python
placeholders = ",".join("?" * len(request_ids))
```

SQLite имеет лимит `SQLITE_MAX_VARIABLE_NUMBER = 999`. При 1000+ заявках `execute()` выбросит `OperationalError`. Сейчас это молча проглатывается `except Exception` на строке 311 — возвращается пустой словарь, фото-количество для всех заявок = 0, без логирования.

**Исправление:** Разбивать на батчи по 900 или использовать temp table + JOIN.

---

### C4. float("5,5") выбрасывает ValueError

**Файл:** `bot.py:524`
**Функция:** `confirm_request`

```python
quantity=float(context.user_data['quantity']),
```

`validate_quantity()` допускает запятую через `.replace(",", ".")`, но строка сохраняется как `"5,5"`. `float("5,5")` в Python не парсит запятую → `ValueError`. Пользователь получит «Ошибка при сохранении заявки».

**Исправление:** Нормализовать перед сохранением: `float(context.user_data['quantity'].replace(",", "."))`.

---

### C5. callback_data превышает 64 байта для кириллицы

**Файл:** `bot.py:829, 1025`
**Функция:** `_show_list`, `_show_list_msg`

```python
safe_v = v[:50]  # 50 символов, но не байт
```

Telegram ограничивает `callback_data` до **64 байтов**. Кириллица = 2-4 байта/символ. 50 символов кириллицы = до 200 байт. Кнопки `rename:` и `del:` с длинными значениями не будут работать.

**Исправление:** Обрезать по байтам, а не по символам. Учитывать длину префикса (`rename:`, `del:`, `confirm_del:`, `bpr:`).

## 🟠 ВЫСОКИЕ — потеря данных, некорректное поведение

### H1. Два админа могут завершить одну заявку дважды

**Файл:** `bot.py:644-745`, `db.py:239-254`
**Функция:** `complete_confirm_handler`, `complete_request`

Два админа одновременно открывают список активных заявок, выбирают одну и ту же заявку и подтверждают завершение. `complete_request()` не проверяет `done_date IS NULL` перед UPDATE. Результат: два уведомления инициатору.

**Исправление:** Добавить `WHERE done_date IS NULL` в UPDATE и проверять `rowcount` после.

---

### H2. Частичное сохранение фото без отката заявки

**Файл:** `bot.py:522-559`
**Функция:** `confirm_request`

```python
request_id = add_request(...)
for file_id in photos:
    add_request_photo(request_id, file_id)  # может упасть на середине
```

Если `add_request_photo` упадёт на 3-м фото из 5, заявка уже создана, 2 фото сохранены, 3 потеряны. Плюс `user_data.clear()` выполняется даже при ошибке — пользователь не может повторить попытку.

**Исправление:** Обернуть в одну транзакцию. При ошибке не вызывать `user_data.clear()`.

---

### H3. Молчаливое подавление Exception в 5 местах

**Файл:** `db.py` — строки 292-293, 311-312, 338-339, 351-352

```python
except Exception:
    return {}  # или return None, или return []
```

Скрывает реальные проблемы: БД заблокирована, повреждена, нет прав. Бот будет показывать «0 фото», «инициатор не найден» без какой-либо диагностики.

**Затронутые функции:**
- `get_request_photos`
- `get_photo_counts`
- `get_initiator_tg_id`
- `get_initiator_by_tg_id`

**Исправление:** Добавить `logger.warning(f"...: {e}")` в каждый except-блок.

---

### H4. Необработанный ValueError при парсинге дат

**Файл:** `core.py:63, 146, 242`
**Функция:** `format_task_html`, `_build_completed_report`, `_build_active_report`

```python
req_date = date.fromisoformat(req_date_str) if req_date_str else None
```

Некорректная строка в БД (не `YYYY-MM-DD`) → `ValueError` → уронит всю генерацию отчёта. Все пользователи не получат отчёт.

**Исправление:** Обернуть в try/except, при ошибке использовать `None`.

---

### H5. Привязка инициатора перезаписывается без удаления старой

**Файл:** `db.py:317-326`, `bot.py:198`
**Функция:** `link_initiator`

`link_initiator(text, user_id)` использует `ON CONFLICT DO UPDATE`, но не удаляет старую привязку пользователя. Если tg_id=123 был привязан к «Алексей», а потом к «Иван», в БД будут обе записи, а `get_initiator_by_tg_id(123)` вернёт только одну.

**Исправление:** Перед `INSERT` удалить старую привязку по `telegram_id`.

---

### H6. Произвольный текст в PHOTO-состоянии молча игнорируется

**Файл:** `bot.py:1104-1109`
**Функция:** ConversationHandler PHOTO state

Если пользователь отправит текстовое сообщение (не фото, не кнопка), ни один handler не сработает. Пользователь не получит ответа и не поймёт, что происходит.

**Исправление:** Добавить catch-all handler для текста в PHOTO-состоянии:
```python
MessageHandler(filters.TEXT & ~filters.COMMAND, handle_photo_text_hint),
```
Где `handle_photo_text_hint` отправит: «📷 Отправьте фото или нажмите кнопку».

## 🟡 СРЕДНИЕ — UX, robustness, архитектура

### M1. Regex 'Настройки' без якорей

**Файл:** `bot.py:1120`

`filters.Regex('Настройки')` совпадёт с любым сообщением, содержащим подстроку «Настройки» (например, «Мои Настройки бота»).

**Исправление:** `filters.Regex('^⚙️ Настройки$')` или `filters.Regex('^Настройки$')`.

**Исправление:** Заменить все `/6` на `/7` (включая строки 365, 385).

### M6. Race condition в complete_request

**Файл:** `db.py:239-254`

SELECT и UPDATE не объединены в один атомарный запрос. Между ними другой процесс может завершить ту же заявку.

**Исправление:** `UPDATE requests SET done_date = ? WHERE id = ? AND done_date IS NULL RETURNING *`.

### M7. URL regex обрезает скобки

**Файл:** `core.py:12-15`

```python
r'https?://[^\s<>"\')\]]+'
```

URL вида `https://ru.wikipedia.org/wiki/Мат_(программирование)` обрежется на первой `)`. Скобки допустимы в URL (RFC 3986).

**Исправление:** Добавить обработку сбалансированных скобок или использовать `urllib.parse`.

### M8. Дублирование форматирования в completed-отчёте

**Файл:** `core.py:139-167`

`_build_completed_report` вручную форматирует каждую заявку вместо использования `format_task_html()`. В completed-отчёте нет эмодзи-индикаторов статуса, другой формат.

**Исправление:** Переиспользовать `format_task_html()` с `photo_count`.

### M9. int(os.getenv(...)) без обработки ошибок

**Файл:** `config.py:28-30`

```python
OVERDUE_DAYS = int(os.getenv("OVERDUE_DAYS", 3))
REPORT_HOUR = int(os.getenv("REPORT_HOUR", 9))
REPORT_MINUTE = int(os.getenv("REPORT_MINUTE", 0))
```

Мусор в env → `ValueError` → бот не запустится. На Amvera переменные задаются через веб-UI, человеческая ошибка вероятна.

**Исправление:** Обернуть в try/except с fallback на значение по умолчанию.

### M10. split_message режет по символу при отсутствии \\n

**Файл:** `utils.py:62-64`

Если `rfind("\n")` возвращает `-1`, `cut` ставится в `max_length`. Разрез идёт по символу, без учёта границ тегов или URL.

**Исправление:** Искать последний пробел в пределах `max_length`.

### M11. Удаление инициатора не чистит initiator_users

**Файл:** `bot.py:938-941`, `db.py:200-207`

Удаление значения из справочника `initiator` не проверяет `initiator_users`. Удалённый инициатор останется привязанным к пользователю.

**Исправление:** При удалении инициатора из справочника удалять соответствующую запись из `initiator_users`.

---

### M12. Дробные числа без форматирования

**Файл:** `core.py:78`

```python
qty_text = f"{qty} {unit}".strip()
```

Значение `2.333333333` отобразится как `2.333333333 кг`.

**Исправление:** `f"{qty:g} {unit}"` (убирает trailing zeros) или `round(qty, 2)`.
